# Отчет: аномалии изоляции в SQL

## Выбранная БД

Для практики выбрана `MySQL 8.4` с движком `InnoDB`.
Сценарии лежат в папке `scenarios/`, таблицы и тестовые данные - в `sql/00_schema.sql`.

`MySQL` выбран потому, что в нем можно показать все четыре аномалии из задания, включая `dirty read` на уровне `READ UNCOMMITTED`.

## Подготовка

```bash
cd prac_tasks/sql_isolation
docker compose up -d
docker exec -i sql-isolation-mysql mysql -uroot -proot isolation_lab < sql/00_schema.sql
```

Для каждого примера открываются две параллельные сессии:

```bash
docker exec -it sql-isolation-mysql mysql -uroot -proot isolation_lab
```

## Таблицы и данные

Используются таблицы:

- `accounts` - счета пользователей, поле `balance` нужно для чтения и обновлений.
- `orders` - заказы, поле `status` нужно для демонстрации фантомных строк.
- `audit_events` - вспомогательная таблица для фиксации событий.

Начальные данные:

| table | key data |
|-------|----------|
| accounts | `Alice = 100`, `Bob = 200` |
| orders | один заказ `new`, один заказ `paid` |

## 1. Dirty read

Файлы:

- `scenarios/01_dirty_read_session_a.sql`
- `scenarios/01_dirty_read_session_b.sql`

Уровень изоляции: `READ UNCOMMITTED`.

Шаги:

1. Сессия `A` начинает транзакцию и читает баланс `Alice`: `100`.
2. Сессия `B` начинает транзакцию и меняет баланс `Alice` на `50`, но не делает `COMMIT`.
3. Сессия `A` повторно читает баланс и видит `50`.
4. Сессия `B` делает `ROLLBACK`.
5. Сессия `A` снова читает баланс и видит `100`.

Результат:

| step | balance |
|------|---------|
| A1: initial balance | 100 |
| A2: dirty read, B has not committed yet | 50 |
| A3: after B rollback | 100 |

Вывод: сессия `A` прочитала незакоммиченное изменение из сессии `B`. После отката оказалось, что значения `50` в зафиксированном состоянии БД никогда не было.

Как избежать:

- Не использовать `READ UNCOMMITTED`.
- Использовать минимум `READ COMMITTED`, где незакоммиченные изменения других транзакций не видны.

## 2. Non-repeatable read

Файлы:

- `scenarios/02_non_repeatable_read_session_a.sql`
- `scenarios/02_non_repeatable_read_session_b.sql`

Уровень изоляции: `READ COMMITTED`.

Шаги:

1. Сессия `A` начинает транзакцию и читает баланс `Alice`: `100`.
2. Сессия `B` меняет баланс `Alice` на `150` и делает `COMMIT`.
3. Сессия `A` в той же транзакции повторяет тот же `SELECT`.
4. Второе чтение в сессии `A` возвращает `150`.

Результат:

| step | balance |
|------|---------|
| A1: first read | 100 |
| A2: second read in same transaction | 150 |

Вывод: один и тот же запрос внутри одной транзакции вернул разные значения.

Как избежать:

- Использовать `REPEATABLE READ` или `SERIALIZABLE`.
- Если строку нужно менять, читать ее через `SELECT ... FOR UPDATE`, чтобы заблокировать до конца транзакции.

## 3. Phantom read

Файлы:

- `scenarios/03_phantom_read_session_a.sql`
- `scenarios/03_phantom_read_session_b.sql`

Уровень изоляции: `READ COMMITTED`.

Шаги:

1. Сессия `A` начинает транзакцию и считает заказы со статусом `new`: `1`.
2. Сессия `B` добавляет новый заказ со статусом `new` и делает `COMMIT`.
3. Сессия `A` в той же транзакции повторяет подсчет.
4. Второй запрос возвращает `2`.

Результат:

| step | new_orders |
|------|------------|
| A1: first count of new orders | 1 |
| A2: second count in same transaction | 2 |

Вывод: во второй выборке появилась новая строка, подходящая под то же условие.

Как избежать:

- Использовать `REPEATABLE READ` для консистентного снимка данных.
- Для операций, где важна защита диапазона строк, использовать `SERIALIZABLE` или блокирующие чтения с подходящим индексом.

## 4. Lost update

Файлы:

- `scenarios/04_lost_update_session_a.sql`
- `scenarios/04_lost_update_session_b.sql`

Уровень изоляции: `READ COMMITTED`.

Шаги:

1. Сессия `A` читает баланс `Alice = 100` в переменную `@old_balance_a`.
2. Сессия `B` читает тот же баланс `Alice = 100` в переменную `@old_balance_b`.
3. Сессия `A` записывает `@old_balance_a + 10`, то есть `110`, и делает `COMMIT`.
4. Сессия `B` записывает `@old_balance_b + 20`, то есть `120`, и делает `COMMIT`.
5. Итоговый баланс равен `120`, хотя корректный результат двух прибавлений должен быть `130`.

Результат:

| expected | actual |
|----------|--------|
| 130 | 120 |

Вывод: обновление сессии `A` потерялось, потому что сессия `B` рассчитала новое значение на основе устаревшего чтения.

Как избежать:

- Делать атомарное обновление: `UPDATE accounts SET balance = balance + 20 WHERE id = 1`.
- Использовать `SELECT ... FOR UPDATE` перед расчетом нового значения.
- Использовать оптимистическую блокировку: добавить `version` и обновлять строку с проверкой `WHERE id = ? AND version = ?`.
- Для критичных операций использовать `SERIALIZABLE`.

## Общий вывод

Аномалии возникают, когда параллельные транзакции читают или меняют пересекающиеся данные без достаточной изоляции и блокировок.
Чем выше уровень изоляции, тем меньше аномалий видно приложению, но тем выше вероятность блокировок и ниже параллелизм.
